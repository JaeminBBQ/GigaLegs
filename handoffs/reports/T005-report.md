## Deviations from the spec
- `award_badges` commits itself (like `log_set`/`log_day`/`log_ride` in this codebase) instead of only flushing, so badge rows can never be lost by a caller that forgets to commit.
- Badge-earned announcements on the summary page reuse the existing `SessionSummary.messages` notice style rather than a new UI element.
- Nothing else; engine functions match the spec signatures and semantics exactly.

## Questions / proposals for Claude
1. **Gated repeat week mapping.** The `gated_repeat` XP event fires on the first lift *after* the repeated week (that's when `resolve_gate` runs), so it protects the calendar week the event happened in — not the repeated week itself. If you want the repeat to protect the *prior* week instead, that's a small change in `week_facts` (shift the event's local date back one week). Which week should count as protected?
2. `/path/bike-stage` (manual stage changes) doesn't call `award_badges` — the spec named only the four call sites. The `commuter` badge therefore awards at the next logged activity after reaching stage 5. Worth adding the call there? (One line.)
3. `active_days` counts lifts, rides, and *recovery* days only — `rest` and `smart_rest` days are not active (smart rest protects the week instead). That's my reading of "days with a lift, ride, or recovery"; flagging in case you meant all logged days.
4. Freeze accounting: `weekly_streak` consumes freezes newest-miss-first, and `freezes_used` counts only freezes consumed while the streak is still alive (older misses behind a dead streak are not "used"). That matches the spec's walk algorithm, but it means the displayed "freezes left" can exceed `earned − all_misses_ever`. Let me know if you'd prefer a different accounting.
